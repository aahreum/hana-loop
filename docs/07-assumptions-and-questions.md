# 가정 및 질문 사항

## 가정한 사항

### 도메인

1. **Scope 분류 자동 결정**: 활동 유형(type)에 따라 Scope 1/2/3이 자동으로 결정된다고 가정.
   - Scope 1: 연료 직접 연소 (경유, LNG, 가솔린)
   - Scope 2: 구매한 전력/열
   - Scope 3: 원소재, 운송, 폐기물 등

2. **배출계수 단일 통화**: 국가별 전기 배출계수가 다르지만, MVP에서는 한국 전력 배출계수(0.4567 kgCO2e/kWh) 단일 적용.

3. **탄소세 계산**: 과제에서 "향후 지불해야 할 탄소세 계획"을 언급하나, 세율이 주어지지 않아 배출량 시각화로 대체. 탄소세 추정값은 별도 설정 가능한 세율 입력으로 확장 가능.

4. **회사 간 비교**: 단일 회사 관점에서 대시보드를 구성하되, 사이드바 드롭다운으로 회사를 전환할 수 있는 구조.

5. **배출량 단위**: 입력은 `kgCO2e`, 대시보드 표시는 `tCO2e` (÷1000)로 통일.

### 기술

6. **인증 없음**: 과제 범위상 로그인/권한 없이 모든 데이터 접근 가능으로 가정. Supabase RLS는 비활성화.

7. **데이터 영속성**: Supabase에 실제 저장. Seed Data는 최초 1회 SQL로 삽입.

8. **다국어 지원 없음**: UI는 한국어/영어 혼용 (레이블은 영어, 설명은 한국어).

## 질문 사항 (실제 서비스라면 확인할 내용)

### 도메인

1. **탄소세 세율**: 국가별/연도별 탄소세 세율 데이터가 있나요? 세율 적용 기준은 어떻게 되나요?

2. **Scope 3 범주**: GHG Protocol Scope 3에는 15개 카테고리가 있습니다. 이번 MVP에서 어느 범주까지 포함해야 하나요?

3. **검증 워크플로우**: 입력된 활동 데이터를 승인/거부하는 워크플로우가 필요한가요?

4. **목표 설정**: 회사별 탄소 감축 목표(target)를 설정하고 현재 달성률을 보여주는 기능이 필요한가요?

5. **규제 보고서**: ISO 14064, GHG Protocol 등 특정 보고 형식으로 export 기능이 필요한가요?

### 기술

6. **다중 테넌시**: 여러 기업 고객이 각자의 데이터만 보는 구조인가요? 이 경우 인증과 행 수준 보안(RLS)이 필요합니다.

7. **배출계수 데이터 출처**: 자체 배출계수 DB를 관리하나요, 아니면 외부 API(IPCC, 환경부 등)와 연동하나요?

8. **실시간 업데이트**: 여러 사용자가 동시에 데이터를 입력할 때 WebSocket/SSE 등 실시간 동기화가 필요한가요?

## 주요 설계 결정 근거

| 결정                               | 대안                                 | 선택 이유                                                                 |
| ---------------------------------- | ------------------------------------ | ------------------------------------------------------------------------- |
| Next.js API Routes + Supabase      | Fake API만 사용                      | 실제 영속성. 가점 요소(PostgreSQL) 충족. 구조가 실서비스와 동일           |
| zod-to-openapi로 Swagger 자동 생성 | OpenAPI spec 수동 작성               | Zod 스키마가 유효성 검증 + API 문서의 단일 소스. 중복 없음                |
| ActivityData와 EmissionResult 분리 | emissions 필드를 ActivityData에 포함 | 배출계수 변경 시 재계산 가능. 감사 추적. 실무 탄소 회계 표준 패턴         |
| 배출계수 validFrom/validTo         | 단순 단일 레코드                     | 규정 변경 시 과거 데이터 무결성 보장. 실제 탄소 관리 플랫폼의 필수 요건   |
| TanStack Query + Zustand 분리      | Context API만 사용                   | 서버 상태(캐싱/동기화)와 클라이언트 UI 상태의 관심사 명확 분리            |
| Recharts 선택                      | Visx, Chart.js                       | React 컴포넌트 모델과 일치. SSR 호환. 충분한 커스터마이징. 번들 크기 적절 |
