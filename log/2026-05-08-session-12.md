## 주요 결정 및 트레이드오프

### 1. Swagger UI 렌더링 방식 — 'use client' 직결 vs dynamic ssr:false

| 방향                           | 장점                              | 단점                                  |
| ------------------------------ | --------------------------------- | ------------------------------------- |
| `'use client'` page            | 단순                              | CLAUDE.md "page는 서버 컴포넌트" 위반 |
| **container를 dynamic ssr:false** ✅ | page는 서버 컴포넌트 유지, swagger-ui-react 의 브라우저 의존성 안전 처리 | container 1단계 추가 |
| `iframe` 으로 별도 호스트       | SSR 회피                           | 다크모드/스타일 동기화 비용           |

→ react-coding-conventions의 page = 서버 컴포넌트 규칙 준수. swagger-ui-react는 DOM API에 의존하므로 SSR 시 BAILOUT_TO_CLIENT_SIDE_RENDERING이 정상 fallback이지만, dynamic ssr:false 로 명시해 의도를 코드에 남김.

### 2. OpenAPI 등록 위치 — 스키마 파일 분산 vs 단일 진입점

| 방향                                        | 장점                              | 단점                                   |
| ------------------------------------------- | --------------------------------- | -------------------------------------- |
| 각 `shared/types/*.ts` 에서 `.openapi()` 호출 | 도메인 응집                       | `extendZodWithOpenApi(z)` 호출 시점 강결합, 테스트/번들 부담 |
| **`shared/lib/openapi.ts` 한곳에서 register** ✅ | 타입 파일은 순수 Zod 유지, 메타데이터는 OpenAPI 진입점 1곳 | 스키마-엔드포인트가 분리됨            |

→ Zod 스키마는 폼 검증/응답 타입 추론이 본업이고, OpenAPI 메타데이터는 부가물. 한 파일(`shared/lib/openapi.ts`)에서 `extendZodWithOpenApi(z)` + `registry.register()` + `registerPath()` 모두 처리.

### 3. `/api/docs` 응답 — 동적 vs 정적

| 방향              | 장점                  | 단점                            |
| ----------------- | --------------------- | ------------------------------- |
| 매 요청 generate  | 변경 즉시 반영        | 매번 generate 비용              |
| **`force-static`** ✅ | 빌드 시 1회 생성      | 스키마 바뀌면 재빌드 필요       |

→ 스펙은 빌드 산출물의 일부로 처리. 빌드 결과에서도 `○ /api/docs` 정적 prerender로 확인됨.
