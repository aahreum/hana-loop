## 주요 결정 및 트레이드오프

### 1. 테스트 범위 — 어디까지 작성할 것인가

| 방향                                | 장점                                      | 단점                                           |
| ----------------------------------- | ----------------------------------------- | ---------------------------------------------- |
| **순수 함수만 (계산+인사이트+스키마)** ✅ | 모킹 0, 빠른 작성/실행, 회귀 방어 가치 ↑ | API/훅 회귀는 통합 환경에서만 잡힘             |
| API Route 3종 세트 추가             | CLAUDE.md 명시 항목 충족                  | Supabase 체이닝/RPC 모킹 비용 큼               |
| TanStack Query 훅 추가              | 통합 검증                                 | QueryClient + fetch 모킹 셋업 비용 매우 큼     |
| 전부 (lib + API + 훅)               | 최대 커버리지                             | 4~5시간 소요, 과제 8~12시간 한도에서 부담 ↑    |

→ ROI 기준 순수 함수에 집중. 0% 영역은 trade-off 문서로 근거 확보.

### 2. 커버리지 0% 영역의 의도적 제외

| 영역                          | 제외 이유                                                                  |
| ----------------------------- | -------------------------------------------------------------------------- |
| `app/api/**/route.ts`         | Supabase 클라이언트(체이닝 + RPC) 모킹 비용 ↑. 모킹해도 실제 SQL 검증 불가  |
| `shared/hooks/**`             | TanStack Query 훅은 얇은 wrapper. fetch만 다시 검증하는 셈                 |
| `useDashboard.ts`             | 통합 훅 — 의존성 7개 모킹 필요                                              |

→ 회귀 보호는 **Vercel 프리뷰 + 수동 시나리오 점검**으로 대체. README/문서에서 trade-off로 풀어쓸 예정.

### 3. 테스트 파일 위치 — co-location vs 별도 디렉토리

| 방향                            | 장점                              | 단점                       |
| ------------------------------- | --------------------------------- | -------------------------- |
| **co-location (소스 옆 .test.ts)** ✅ | 검색·이동·삭제 동기화 쉬움        | 빌드 시 제외 필터 필요     |
| `__tests__/` 별도 디렉토리      | 빌드 산출물 분리 명확             | 폴더 두 번 오가야 함       |
| `test/` 루트 디렉토리           | 통합 테스트와 자연스러움          | 단위 테스트엔 과함         |

→ 단위 테스트 위주이고 vitest config의 include로 충분히 분리되므로 co-location 채택.
